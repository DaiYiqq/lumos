# 检索层设计与效果评估

> 本文记录 Lumos 混合检索的实现方式，以及「单一检索 vs 混合检索」的实测对比数据。
> 数据由仓库内的可复现测试生成，不是估算值。

## 1. 架构

```
提问
 ├─ 向量检索：问题 → BGE-small-zh-v1.5 (512 维) → sqlite-vec KNN top-K
 └─ 关键词检索：问题 → FTS5(trigram) BM25 top-K
        └─ RRF 融合（k = 60）→ top-N chunk → 带出处返回
```

- **向量**：`fastembed` + ONNX Runtime，模型 `BAAI/bge-small-zh-v1.5`（512 维），
  首次使用时下载约 95MB，缓存在应用数据目录 `models/`。
- **关键词**：SQLite FTS5 外部内容表，`tokenize='trigram'`，因此中文子串可以命中。
  查询侧把中文按 3 字滑窗拆词后 OR，兼顾「一句话式提问」与精确术语。
- **融合**：Reciprocal Rank Fusion，`score = Σ 1 / (60 + rank)`。
  RRF 只依赖名次，不需要把「向量距离」和「BM25 分数」归一化，这也是选它的原因。

## 2. 效果评估

### 方法

- 语料：24 篇 Markdown 文档
  - 8 篇「关键词型」：每篇包含一个唯一工单编号（如 `WX-7351-AB3`），查询就是编号；
  - 8 篇「语义改写型」：查询与原文几乎不共享三字子串（例如问「对方反悔时最多能要求多少补偿」，
    原文写「任何一方反悔，需要支付的金额不得超过合同总额的百分之二十」）；
  - 8 篇无关干扰文档。
- 指标：**recall@3**，16 条查询，命中即该查询对应的源文件出现在前 3 条结果中。
- 三种模式使用同一套数据与同一查询，仅切换检索通道。

### 结果（2026-10-18，本机实测）

| 模式                   | recall@3  |
| ---------------------- | --------- |
| 仅关键词（BM25）       | **0.750** |
| 仅向量（BGE-small-zh） | **0.688** |
| **混合（RRF）**        | **1.000** |

混合检索相对纯关键词 **+25 个百分点**，相对纯向量 **+31.2 个百分点**：
关键词通道负责编号、术语等精确匹配，向量通道负责语义改写，两路互补后覆盖了全部查询。

### 复现命令

```bash
# 首次会下载约 95MB 模型；国内网络建议设置镜像（也可设置 HF_ENDPOINT，程序会优先使用）
cd src-tauri
LUMOS_EMBEDDING_EVAL=1 HF_ENDPOINT=https://hf-mirror.com \
  cargo test hybrid_beats_single_retrievers -- --nocapture
```

输出示例（Windows 控制台按 GBK 显示中文可能乱码，数字不受影响）：

```
=== 检索效果对比（16 条查询，recall@3）===
keyword : 0.750
vector  : 0.688
hybrid  : 1.000
```

## 3. 工程细节

- **模型下载**：不使用 hf-hub（对镜像站的 range 响应兼容性差），
  而是直接 HTTP 下载 5 个模型文件，按 `HF_ENDPOINT` → 官方 → `hf-mirror.com` 的顺序容错。
  任一站点成功即缓存；全部失败时自动降级为纯关键词检索，应用仍可用。
- **异步就绪**：模型在后台线程加载，不阻塞窗口启动；加载期间导入的文档先入库，
  模型就绪后由补写任务自动生成向量（`retrieval::backfill`）。
- **查询指令**：按 BGE 官方建议，查询侧加前缀「为这个句子生成表示以用于检索相关文章：」，
  文档侧不加前缀。
- **维度固定**：`chunks_vec` 为 `float[512]`；更换嵌入模型需要新增迁移并重建向量。

## 4. 已知限制

- 评估语料是合成的小规模数据，结论用于验证「双通道互补」这一设计假设，不代表真实语料的绝对水平。
- 暂未启用 cross-encoder rerank（任务书里的进阶功能），计划在 P6/P7 评估收益后再决定是否默认开启。
- 首次使用需要下载模型；离线环境或下载失败时自动降级为关键词模式，并在 UI 中明确提示（P5）。
